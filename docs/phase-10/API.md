# Device operations API — format 1

All customer APIs require the existing authenticated browser session and live workspace capability; server mutations enforce same-origin checks. Responses are private/no-store. API keys from Phase 9 do not gain device-operation scopes. UUIDs and bounded page parameters are validated. Errors return safe codes/messages, not private credentials.

- `GET /api/device-operations?orgId=UUID&page=0&deviceId=UUID` returns public keys, newest 100 artifact summaries, newest 50 rollouts, 50 profiles/operations on the selected page and optional device filter. Transfer byte totals are decimal strings. No credential roots or download tokens appear in this response.
- `GET /api/device-operations/rollouts/UUID?orgId=UUID&page=0` returns 50 snapshotted target records, eligibility reasons and operation status plus total count.
- `POST /api/device-operations/action`: `{orgId,action,data}`. Actions: `key` (id/name/publicPem), `revoke_key` (id), `artifact` (manifest/signature/releaseNotes/channel), `approve` (id), `enable_device` (id/enabled), `confirm` (id/kind/confirm:true), `pause`, `resume`, `advance`, `cancel` (rollout id/kind). Uploaded/verified is not a public action. Owner/admin control trust, approval, deployments and cancellation; developer can upload firmware and draft configuration; operator/viewer read only. Confirm independently checks the stored rollout kind and live permissions.
- `PUT /api/device-operations/artifacts/UUID?orgId=UUID`: application/octet-stream compiled image, exact signed length/hash, at most 4 MiB. Only immutable drafts accept content. An orphaned identical object can be finalized safely after a failed response/database call; content is never overwritten.
- `POST /api/device-operations/preview`: `{orgId,requestId,definition}`. Repeating requestId with the same definition returns the existing draft; different content conflicts. `definition.kind` is firmware/configuration; provide artifactId or typed configuration. Selection supports ids, group, tag, all:true, optional hardwareModel/firmwareVersion filters. Cumulative wavePercentages end at 100 (at most six), manualAdvance defaults true, observationSeconds 0–86400, minimumSamples 1–1000, failurePercent 0–100, maxConcurrent 1–100, perMinute 1–1000, timeoutSeconds 60–604800, startsAt/endsAt UTC timestamps with a maximum 30-day window. No selection is implicit.

```json
{"orgId":"YOUR_WORKSPACE_UUID","requestId":"NEW_REQUEST_UUID","definition":{"kind":"configuration","configuration":{"reportIntervalSeconds":300,"sampleIntervalSeconds":60,"diagnosticLevel":"error"},"selection":{"ids":["YOUR_DEVICE_UUID"]},"wavePercentages":[1,10,25,100],"manualAdvance":true,"observationSeconds":60,"maxConcurrent":10,"perMinute":30,"failurePercent":5,"timeoutSeconds":3600}}
```

Customer API inputs above use illustrative UUID labels; replace them with your actual authorized UUIDs. A preview returns `{id}` and must be explicitly confirmed before assignment. The server retains the snapshot and audit request identity. Mutations are rate-limited: 60 management API requests/user/workspace/minute and 120 administrative database operations/workspace/hour. Quota exhaustion is a real error, not fabricated success. No action changes subscription pricing.

## Device-only HTTPS API

`POST /api/device-management/challenge` accepts `{wireDeviceId,bodyHash}` and returns `{id,nonce,expiresInSeconds:60}`. The service creates a cryptographically random 32-byte nonce and stores only its hash. A maximum 60 challenges/device/minute limits abuse. Do not infer possession of a credential merely from receiving a challenge.

`POST /api/device-management/message` accepts `{wireDeviceId,challengeId,nonce,payload,mac}`. Payload is canonical base64 of the exact UTF-8 JSON `{action,data}`; HMAC format is in IMPLEMENTATION.md. Actions: capabilities, poll, report. One-use consumption and state mutation share a transaction. A lost response requires a fresh challenge carrying an idempotent report, not reuse of an old nonce. Capabilities never grant approval. Poll returns null or an assigned operation with generation; firmware includes its signed canonical manifest, signature, key fingerprint and a fixed operation download path/token.

`GET /api/device-management/download/OPERATION_UUID` requires `Authorization: Bearer ota_TOKEN_UUID.SECRET_HEX`. Tokens are operation/current-epoch-scoped and expire in ten minutes. No secret goes in the URL. One `Range: bytes=START-END` is supported; no redirects/arbitrary source URLs. The agent verifies the full signed image after download even if transport succeeded. Requests are certificate-verified HTTPS; only an explicit isolated loopback fixture may use HTTP. Revoked/disabled devices, revoked keys, disabled management profiles and unavailable operations cannot authorize a new download. Existing in-flight bytes cannot be recalled.

Report data requires id, generation, stage and safe optional category. Applied requires exact typed configuration. Healthy requires the expected sha256/securityVersion and healthValidated:true after the reboot transition. Server records receipt timestamps and authenticated-claim provenance. No generic arbitrary-command or secret-configuration API exists.

Execution-window semantics: poll responses include bounded remaining seconds. New polls/downloads are refused once the rollout/operation window closes. Reference agents conservatively subtract request duration and check their local monotonic deadline before starting configuration or selecting a boot partition. Already-started transfers/installation and later health/rollback reconciliation may finish after the window; a server pause/cancel cannot recall physical work. No hard real-time physical completion deadline is promised. Firmware transfer observations are best effort with bounded finalization, not billing-grade metering or proof the remote device received every byte.

## Per-device identity across a shared image

Managed firmware must load its existing Secure V2 wire ID/root from the optional persistent `sv2_identity` NVS record. This is the same enrollment identity and replay namespace, not a second credential system. The generated private `struct` factory environment consumes the existing one-use bootstrap and persists that identity; a common `struct-ota` build excludes compiled device IDs/roots/bootstrap tokens and loads each device's own record. Missing or corrupt state fails closed. Never clone NVS or a factory firmware across devices. Physical replacement requires fresh server-issued credentials and explicit factory reprovisioning; normal OTA cannot rotate credentials. Device flash/NVS protection still requires separately qualified hardware controls; no eFuses are programmed.

The signed manifest requires `identityMode: "persistent-nvs-v1"` as part of its canonical identity contract. The offline signer, upload route and reference agents reject the known factory-credential image marker, including a legitimately signed factory-tagged artifact. This catches accidental distribution of the supplied factory builds. It cannot prove arbitrary custom firmware is free of malicious credential access: authorized signing keys remain trusted software publishers. Only upload `struct-ota/firmware.bin`; `firmware.factory.bin` is a merged manufacturing image and is unsupported for OTA. The generator sets the default environment to the private factory build, avoiding an initial upload of both environments before provisioning completes.
