# Phase 10 implementation — October 16, 2026

## Architecture and trust

The management plane is separate from Secure V2 telemetry and legacy STRC. Current device root + big-endian wire ID derive a 32-byte HKDF-SHA256 key with info `struct.management.v1`. A device hashes the exact UTF-8 JSON message and requests a random server challenge. The HMAC input is `STRUCT-MANAGEMENT-V1\nWIRE\nCHALLENGE_UUID\nNONCE_HEX\nBODY_SHA256_HEX`. A successful request consumes the nonce in the same transaction as its action. Nonces expire in 60 seconds; nonce replay, body tampering, revoked/disabled/current-epoch mismatches and the enterprise recovery gate deny management. TLS certificate verification remains mandatory, even though freshness does not depend on a device clock.

P-256/SHA-256 manifests use an exact ASCII field order and strict bounds in `protocol/management/core.cjs`, mirrored in `struct_management_crypto.h`. The signature binds workspace, artifact/key UUIDs, platform, model/revision, version, application security version, agent/bootloader requirements, full length and hash. Private signing keys remain offline. Server registration never changes device trust; pins are explicitly provisioned. This is authenticated agent evidence, not secure-boot attestation.

Artifacts use a private Supabase Storage bucket. The explicit filesystem adapter is for isolated tests. Uploads stream to bounded temporary files, check signature/length/hash/header and write immutable object identities. A retry after object creation but before SQL finalization verifies existing size and every byte without overwriting it. Uploaded is a private server action, never a public browser verb. Download tokens are operation/epoch-scoped, hashed at rest, ten-minute bounded and carried in Authorization headers. Range downloads remain bounded and private; no arbitrary URL is accepted. Four upload/eight download streams per web process are reserved synchronously. Hosted Storage has not been qualified in this task.

## Database and scheduling

Migration 041 adds `management_settings`, `firmware_signing_keys`, `firmware_artifacts`, `device_management_profiles`, `management_challenges`, `firmware_rollouts`, `rollout_targets`, `device_operations`, `device_operation_events`, `firmware_download_tokens` and `firmware_transfer_metrics`. New tables and RPCs are service-only with RLS and live server-side capabilities. Restrictive Storage policy denies this bucket to browser/anonymous clients even if a historical broad policy exists. Immutable artifact identities, device/generation and rollout/device uniqueness plus one-active-operation/device constraints enforce invariants.

Preview is idempotent per workspace/request UUID, snapshots current device/group/tag membership and credentials/capabilities, records ineligibility reasons and never issues a command. Confirmation requires explicit administrator authorization and records the approver. A transactional SKIP LOCKED scheduler processes at most 100 assignments/tick, bounded concurrency and per-minute limits. A crashed transaction rolls back; a committed assignment survives worker restart. There is no in-memory firmware queue or external network call in the telemetry hot path.

Waves use deterministic cumulative percentages. Manual advancement is default. Every target in a wave must succeed and meet observation/sample gates. Failure or unknown thresholds pause scheduling. Changed permissions, credentials, eligibility or a rollout window also pause. Pausing/canceling cannot undo bytes or commands already delivered; only unstarted work is canceled. Timeout is Unknown. A late terminal report reconciles only a current generation where applicable. Generations stop before unsafe JavaScript integer precision.

Capabilities are authenticated claims and require explicit opt-in per epoch. Changes to hardware/trust/partition/OTA capability invalidate approval; ordinary reported firmware/security changes do not silently reset the profile. Reported configuration is separate from desired configuration and updates only after a matching applied acknowledgment. Typed settings exclude secrets, schemas and arbitrary code. Revert by publishing a new generation with previous values. Healthy requires the expected image hash/security version and health assertion after reboot transitions.

## Product and monitoring

Firmware and Device Operations pages reuse dashboard styling, roles and navigation. They provide public-key registration/revocation, signed artifact upload/approval, target preview/reasons, staged controls, capability approval, desired/reported state, paginated device operations, target history and expandable evidence timelines. The device dashboard links directly to its management filter. Detailed state uses server evidence versus authenticated claims explicitly. UI requests discard stale tenant responses. Original telemetry starters remain unchanged unless management is explicitly included.

The existing alert evaluator gains `rollout_failures`, the number of safety-paused rollouts in the selected device/group/tag scope. Existing durable incidents, cooldowns, acknowledgment and email/webhook notification paths are reused. No notifications are enabled automatically. Transfer counters count actual server response bytes and remain separate from telemetry and carrier estimates.

## Bounds and remaining limitations

Artifacts: 4 MiB/image; 512 MiB reserved/workspace. Rollouts: 10,000 targets; six cumulative waves; 100 concurrent/device operations and 1,000 starts/minute per rollout. Request and configuration bounds are enforced. Challenge/token cleanup is bounded; transfer observations are 30-day metadata. Terminal operation/target history of completed or canceled rollouts expires after 90 days in bounded cleanup batches; paused/in-flight work is preserved. Operational metadata quotas bound each workspace to 100 signing keys, 1,000 artifact definitions, 1,000 retained rollouts and 1,000,000 retained target decisions. These are safety limits, not new subscription tiers. Automated artifact/object deletion remains unsupported; review quota/retention policy before broad rollout.

This version does not implement delta images, remote bootloader/partition updates, arbitrary commands, Python/Rust/STM32/Linux firmware agents, signed private-network URLs, automatic trust-pin rotation, named-canary group overrides, fleet-wide egress pacing across multiple web processes, or cryptographic remote attestation. Distribution supports byte ranges, but agents restart an interrupted download rather than persist resumable chunk journals. Failure recovery is explicit: repair the cause and create a new rollout, or let the qualified device bootloader restore its prior image. Raising the application security floor intentionally prevents a lower-version rollback release; provide a compatible recovery release at or above the floor.

ESP source/object and complete configuration-capable image builds plus host A/B simulation are useful evidence, not physical OTA acceptance. Physical ESP flash/reboot/power-cut tests, watchdog qualification, hosted Auth/Storage tests, 10,000-device sustained HTTPS/egress tests and production operational approval remain release prerequisites. No production system was changed.

Execution-window semantics: poll responses include bounded remaining seconds. New polls/downloads are refused once the rollout/operation window closes. Reference agents conservatively subtract request duration and check their local monotonic deadline before starting configuration or selecting a boot partition. Already-started transfers/installation and later health/rollback reconciliation may finish after the window; a server pause/cancel cannot recall physical work. No hard real-time physical completion deadline is promised. Firmware transfer observations are best effort with bounded finalization, not billing-grade metering or proof the remote device received every byte.

## Per-device identity across a shared image

Managed firmware must load its existing Secure V2 wire ID/root from the optional persistent `sv2_identity` NVS record. This is the same enrollment identity and replay namespace, not a second credential system. The generated private `struct` factory environment consumes the existing one-use bootstrap and persists that identity; a common `struct-ota` build excludes compiled device IDs/roots/bootstrap tokens and loads each device's own record. Missing or corrupt state fails closed. Never clone NVS or a factory firmware across devices. Physical replacement requires fresh server-issued credentials and explicit factory reprovisioning; normal OTA cannot rotate credentials. Device flash/NVS protection still requires separately qualified hardware controls; no eFuses are programmed.

The signed manifest requires `identityMode: "persistent-nvs-v1"` as part of its canonical identity contract. The offline signer, upload route and reference agents reject the known factory-credential image marker, including a legitimately signed factory-tagged artifact. This catches accidental distribution of the supplied factory builds. It cannot prove arbitrary custom firmware is free of malicious credential access: authorized signing keys remain trusted software publishers. Only upload `struct-ota/firmware.bin`; `firmware.factory.bin` is a merged manufacturing image and is unsupported for OTA. The generator sets the default environment to the private factory build, avoiding an initial upload of both environments before provisioning completes.

Additional compatibility limits: artifact compatibility currently checks hardware, platform, agent/bootloader, partition capacity, trust pins, credential epoch and security floor. Publishers must manually verify the firmware’s immutable schema-slot requirements for every selected device; automatic schema-layout requirement binding is not yet implemented. Observation gates wait after initial authenticated health success; they do not provide continuous post-validation application attestation or automatically consume every fleet-monitoring metric. Qualify these application-specific conditions before rollout.
