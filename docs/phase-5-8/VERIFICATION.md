# Phases 5 + 8 implementation and verification

Verified locally on October 13, 2026. Production has not been modified. No deployment, production migration, customer notification or physical-device test was performed. This report describes a working default-off release candidate and its limits, not completion of every requested production acceptance criterion.

## What changed

The audit found working Secure V2 storage/replay/receipts, durable delivery infrastructure, integration routing and fleet groups/tags in the existing uncommitted changes. It found no scheduled fleet evaluator, durable alert lifecycle, usage rollups or trustworthy persisted historical packet-byte accounting. Retained decoded values cannot establish historical network usage.

The implementation adds actual Secure V2 byte metadata, a durable metrics source and grouped minute/hour/day rollups; durable last-successful-commit state; scheduled/event-driven/no-expectation policies; automatic inactivity and bounded threshold evaluation; deduplicated incidents with acknowledgment, recovery, suppression and history; reliable notification scheduling intents; shared signed webhook dispatch and fenced opt-in email delivery. APIs, responsive Monitoring/Analytics/Alerts pages, usage export, exact counters, explicit cost preferences and real-codec sample insights are connected to those database records.

Important corrections found by fault testing include optional metrics rollback isolation, aggregation transaction recovery, notification enqueue failure preserving the incident, destination snapshot preservation when a rule changes, SQL-numeric preservation for 64-bit thresholds, missing sensor evidence staying unavailable, rule-create retry idempotency, optimistic edit conflicts, rule-limit enforcement with client UUIDs, private notification metadata SELECT restrictions, and explicit gap recording before an expired unprocessed observation is removed.

The production Secure V2 wire format, authentication, replay lifecycle, immutable schemas and commit receipt contract remain unchanged. No firmware change is needed for server-side monitoring. Schema/batch recommendations require deliberate SDK/firmware work and never modify deployed devices automatically.

## Packet and recovery evidence

The original actual serializer regression still yields 9-byte sensor payload / 34-byte application / 62-byte minimum IPv4 uplink. Explicitly lossy optimized encoding yields 3 / 28 / 56 bytes and humidity approximately 61.3. These are tests of that schema/precision policy, not constants used for every device.

The new tests transmit real local encrypted frames and confirm actual payload/framing/tag totals, batch reading counts, duplicate behavior and 21-byte socket-submitted receipts. Optional metric failure does not undo telemetry. A simulated database transport outage does not produce a false committed receipt. Wrong AEAD packets are not attributed to a legitimate tenant. Float64 uses a value requiring more precision than Float32; large integer wrappers remain exact through decoding, alert SQL comparison and string DTOs.

PGlite fault tests cover aggregation rollback/restart, notification enqueue failure with durable retry intent, changed rule destinations, lease fencing, preference changes, replay/backfill after raw metadata cleanup, tenant RLS and service-only RPC restrictions. Disposable real PostgreSQL tests run two aggregators and concurrent incident evaluators, terminate a backend inside an uncommitted rollup transaction and verify exact recovery. Payload metrics and logical readings do not double count.

Email provider behavior is tested with a fake fetch contract and disposable credentials. Webhook notification signing/claims use the actual shared pipeline. Real Resend acceptance/mailbox delivery, hosted authentication/PostgREST and production customer destinations remain **unverified**. Failed notifications preserve incidents. Queueing a notification is never labeled as successful external delivery.

## Performance evidence

The accompanying JSON contains full timestamps, sample counts, boundaries, memory/CPU observations where measured and the current migration SHA256. No carrier traffic, physical-device capacity or million-device claim is derived from these tests.

- Real disposable PostgreSQL 18.4, 500 SQL commits/stage: migration-037 baseline median **0.615 ms**, p95 1.028 ms, 1462.8 commits/s; observed idle median **0.807 ms**, p95 1.191 ms, 1106.8 commits/s; observed with concurrent aggregation median **0.800 ms**, p95 1.098 ms, 1202.3 commits/s. Idle median instrumentation overhead is **0.192 ms** in this local test, and throughput decreases. These exclude UDP/crypto and Supabase network latency.
- Two actual SQL aggregators completed 1,000 logical readings exactly once; the mixed sample processed 586 observations in 457.3 ms. Mean analytics query was 0.514 ms; measured alert evaluation was 1.297 ms. Concurrent incident deduplication and terminated-backend rollback/recovery passed. All 1,500 telemetry events and 1,500 outbox intents remained consistent. Post-load relation sizes were 770048 bytes packet metrics, 122880 rollups and 172032 identities. Coordinator RSS 82.4 decimal MB excludes PostgreSQL child processes.
- Actual Node AEAD/frame processing with local PGlite, 500 packets/stage: metrics-off median **1.824 ms** and 512.0 packets/s; metrics-on median **2.141 ms** and 428.5 packets/s; batch-of-ten median 3.684 ms and 2591.7 readings/s. Median added work is 0.317 ms. Loop throughput includes simulated-device encryption; latency excludes that frame creation. This is not a UDP/hosted/physical benchmark. RSS 477.6 decimal MB and CPU counters include the embedded database. Canonical accounting covered 5,500 monitored readings; baseline and warmup readings were deliberately not invented in metrics.
- Synthetic inventories at 10, 100, 1,000, 10,000 and **100,000 devices** were exercised. At 10,000: bounded inventory median **32.92 ms** / 20281 JSON bytes; usage **24.66 ms** / 3143 bytes; group usage 18.76 ms; alert evaluation 10.48 ms.
- At 100,000 synthetic records: bounded inventory median **366.52 ms** / 20274 JSON bytes; usage **330.05 ms** / 3169 bytes; group usage 235.17 ms; alert evaluation 102.53 ms. The final 90,000-row increment aggregated in 7333.0 ms (12273 observations/s). RSS 1766.0 decimal MB includes PGlite. These are synthetic metadata/counters plus one real authenticated sample, not secure provisioning or a physical fleet. The increased latency and memory are measured scale constraints, not hidden by browser-side filtering.

The grouped rollup implementation replaced repeated per-event upserts. Preserved pre-grouping evidence has a 786,432-byte rollup relation; the final local sample has a 122,880-byte relation. These include PostgreSQL indexes/MVCC/dead tuples and were separate local runs, so this is evidence motivating reduced write amplification, not a universal storage-saving percentage. Exact WAL bytes, database CPU, production worker RSS, hosted API latency, sustained customer load and frontend before/after LCP/INP were not measured. Browser scenario duration is not a page-performance metric.

## Remaining limits and deployment readiness

This is ready for **staging/deployment review**, with explicit gates. It is not production-qualified and does not satisfy every broad acceptance item yet.

- No live provider/email delivery, hosted Supabase session/PostgREST qualification, physical radio/modem traffic, physical battery measurement or physical-device test. The 100,000-device dataset is synthetic; no sustained production-scale soak was run.
- The UDP listener remains IPv4. IPv6 calculations and processor/SDK tests do not claim an IPv6 production listener rollout. Legacy/TCP packet usage, full cellular/link traffic and downstream HTTP/TLS wire bytes remain unavailable.
- Authenticated rejection/duplicate/socket-receipt observations are best effort. Canonical metric failure and expired durable backlog have gaps; a process crash before buffering can be unknowable. Metrics have bounded retention and are not an unlimited accounting ledger.
- Sensor alerts support one device's scalar numeric/exact integer field. There is no boolean/string/nested expression engine, relative anomaly baseline, automatic reporting-interval inference or per-sensor continuous physical-state proof.
- Group/tag filtering and rule scopes work. Project scope uses the application's organization/workspace model; no independent project system was invented. The existing Devices activity badge retains its older heuristic; Monitoring has the explicit schedule-based result. Device health is a filtered Monitoring view, not a full redesign of every existing device tab.
- Notification preferences are verified-account email opt-in/severity; webhooks use existing generic signed destinations. There is no new notification-recipient directory. Rules, incident openings, transport scheduling and evaluation are capped; delays/terminal failures are visible. Full alert-storm/staging sustained-load qualification remains required beyond deterministic deduplication, limits and concurrency tests.
- Efficiency comparisons use the latest retained sample and verified codecs, not whole-fleet value distributions. Lossless schema suggestions cover representable fields; unsupported mappings stay unavailable. Protocol Lab remains the place to declare lossy precision and inspect broader profiles. Fleet-wide competitor savings are not automatically inferred.
- Cost configuration accepts decimal-MB pricing, integer cellular percentage, period days, measured overrides, allowances/minimums and fleet-level rounding. Per-device carrier increments, actual cloud-provider message billing, automatic carrier feeds and GB-price input are not implemented. Missing/incomplete observations block estimated-network projections unless an explicit carrier override supplies the basis.
- Frontend keyboard/overflow/browser checks passed, but a complete screen-reader/assistive-technology audit is outstanding. Build warnings and deployment packaging need hosted qualification. Local benchmarks include embedded SQL costs and cannot size production workers directly.

Rollout order is reviewed migrations 035–038, disabled instrumentation deployment, explicit staging collection/worker activation, API/UI activation, controlled policy/notification tests, hosted performance/security verification, then separately approved customer rollout. Rollback must pause alerts before disabling their data source and retain queued work/history/identity. See DEPLOYMENT.md for exact commands, flags, prerequisites and recovery procedures. Nothing here authorizes or executes deployment.
